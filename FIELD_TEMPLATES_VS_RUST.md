# Field arithmetic: what Rust programmers do, and what the templates add

This note states how finite-field arithmetic is produced in the Rust ecosystem
today and where the compiler's field templates differ. It accompanies the
benchmark in `bench/fiat_rust_compare/` (dev tree), which measures the Rust the
templates print against the `fiat-crypto` crate on the same inputs.

## What Rust programmers do

Three generic field implementations are in wide use:

| Crate | Mechanism | Arithmetic |
|---|---|---|
| `crypto-bigint` (RustCrypto) | const generics: `Uint<LIMBS>`, `MontyForm`, `ConstMontyForm` | Montgomery at any odd modulus |
| `ff` / `ff_derive` (zkcrypto) | proc-macro from a modulus literal | Montgomery |
| `ark-ff` (arkworks) | `MontBackend<Config, N>`, `#[derive(MontConfig)]` | Montgomery |

For the curves that carry the most traffic these templates are not used. The
`p256` and `k256` crates vendor field code generated by fiat-crypto
(`fiat_p256_mul`, `fiat_secp256k1_montgomery_mul`), and `curve25519-dalek` ships
hand-written radix-2^51 code. The reasons are four.

1. Specialisation. A const-generic template knows the limb count, not the prime.
   Solinas reduction (P-256, P-384, 2^255 − 19), the radix (saturated 2^64 or
   unsaturated 2^51) and the shape of the carry chain are decisions per prime.
   Rust's const generics cannot express them: a product of `N` limbs has `2N`
   limbs, and `generic_const_exprs` is unstable.
2. Proof. The template crates are tested; fiat-crypto's output is proved in Coq.
   A curve crate adopts a generated file for its proof pedigree, not a template
   crate for its convenience.
3. Constant time. Rust gives no guarantee; a template written with `subtle`-style
   selects still leaves `rustc` free to branch. Straight-line generated code with
   mask arithmetic is the accepted compromise.
4. The deliverable. A maintainer wants a `.rs` file to read, review and vendor,
   not a type-level construction to trust.

So the ecosystem's answer to "generic field arithmetic" is generated code with a
proof, and the generator is fiat-crypto.

## What the templates add

The templates are written in Lean, not Rust, and so are not bound by Rust's
generics.

- Specialisation per record. `montTemplate P` and `solinasTemplate S` take a
  modulus record and produce the limb program for that prime; the choice of
  reduction is a choice of template, made once per prime, as fiat makes it.
- One proof for every instance. `FieldTemplate.route_abi_denote` and
  `field_correct_bytes` are stated at every `LimbParams n`; an instantiation
  inherits the theorem and proves nothing new. fiat-crypto proves each generated
  file by running its certified pipeline; the template proves the generator.
- Two outputs from one program. The same `Com jasminDialect` program goes to the
  owned x86 back end (verified bytes, `.o` without an assembler) and to the Rust
  printer (`Jasmin/ComToRustEmit.lean`, fiat's straight-line style with `u128`
  products and `u64` carries). The Rust text is for reading and for `rustc`'s
  scheduling; the bytes are for shipping with the proof.
- Constant time at the bytes. The owned back end's leak theorems hold of the
  shipped object; the printed Rust has the same caveat as fiat's output.

What the templates do not yet have: a theorem relating the printed Rust to the
`Com` (row RUST-PRINT-VERIFY), and the performance comparison itself. The
benchmark decides whether the template's printed code matches fiat's on P-256,
secp256k1 and P-384; adoption follows fiat's precedent only if it does.
